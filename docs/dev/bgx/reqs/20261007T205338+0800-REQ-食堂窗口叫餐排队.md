## 1. 理解复述

**用户要解决的事：** 学校食堂窗口排队信息不透明。用餐者要能按食堂/楼层看到窗口和排队人数，登录后取号，随时看到自己的号和当前叫到哪；窗口员工负责叫号；管理员维护食堂与窗口。要按真实上窗使用，而不是纯演示页。窗口现场还要有大屏显示和语音播报。

**已确认的产品判断：** 纯排队叫号，一期不做点餐、购物车、支付。实时通道用 WebSocket。账号一期自建学号+密码。过号等待时长由管理员按窗口配置，默认 `0`（仅手动过号）。大屏/语音用窗口网页全屏页 + 浏览器播报，不绑定实体叫号器品牌。终端一期为 Web/H5 + 大屏页，不做小程序/App。

## 2. 目标用户与业务问题

| 角色 | 状态 | 说明 |
| --- | --- | --- |
| 用餐者（学生/教职工） | 已确认 | 学号登录；选食堂/楼层/窗口；取号；看自己的号、当前号、前面还有几人；取消等待中的号 |
| 窗口员工 | 已确认 | 登录后只操作被授权窗口：叫下一号、完成、过号、暂停/恢复取号；可打开本窗口大屏页 |
| 食堂管理员 | 已确认 | 维护食堂、楼层、窗口、营业状态、员工授权、用餐者账号、各窗口过号时长 |
| 运维 | 暂定 | 部署与观察高峰在线；未指定专人。不影响核心范围 |

业务问题：高峰不知道哪个窗口人少、不知道排到哪、窗口缺少统一叫号和现场提示。

## 3. 需求条目

### 3.1 核心能力（已确认）

- **R01 食堂 / 楼层 / 窗口浏览**  
  P0。用餐者先选食堂，食堂有楼层则再选楼层，再看窗口。跨食堂队列与号段互不干扰。**列表、人数、当前号摘要必须登录后可见**（D22）。未登录不能匿名刷窗口接口。  
  验收：未登录读列表 → `UNAUTHENTICATED`；登录后 ≥2 个食堂、其中 1 个含楼层时，能钻取到正确窗口列表。

- **R02 窗口排队人数**  
  P0。人数 = 该窗口「等待中」有效号数量；不含已完成、已取消、已过号、已叫号未完成。  
  验收：人数与权威队列一致；叫号/取消/过号后人数立即按规则变化。

- **R03 取号**  
  P0。必须登录。窗口营业中且未暂停取号才可取号。同一人同一时间只能持有 1 个有效号（等待中或已叫号未完成）。同一窗口重复取号返回已有号码，不发新号。号段按窗口、按营业日从 1 递增。  
  验收：未登录被拒绝；已有其他窗口有效号时不能再取；重复点击不产生第二张号。

- **R04 我的号码**  
  P0。展示号码、食堂/窗口、当前号、前面还有几人、状态。同一学号换设备再登录仍能看到有效号。  
  验收：退出再登录号码仍在（未过期/未完成前）。

- **R05 当前号实时展示**  
  P0。持有该窗口号或正在看该窗口的用户，经 WebSocket 收到当前号、人数、窗口状态变化。大屏页使用同一权威数据。  
  验收：员工叫下一号后，用餐者端与大屏无需手工刷新即可与权威数据一致。

- **R06 窗口员工叫号操作**  
  P0。叫下一号、标记完成、过号、暂停取号、恢复取号。只能操作被授权窗口。手动过号始终可用，不依赖是否开启自动过号。  
  验收：无授权操作被拒绝；合法操作后 R02/R05/R22 同步。

- **R07 窗口主数据与营业状态**  
  P0。名称、食堂/楼层、档口编号、营业中/休息/暂停取号。休息或暂停时不能新取号。  
  **打烊（休息/`closed`）后：** 当日已发出的 waiting 号，授权员工可继续叫号/完成/过号，直到叫完或营业日切分作废（D21）。一期不强制「一键批量过号」。暂停取号（`pause_take`）同样：不可新取，可叫已有 waiting。  
  验收：管理员把窗口设为休息后，已登录用餐者仍能看见该窗口且不可取号；员工仍可对当日 waiting 叫下一号。

- **R08 自建学号+密码登录**  
  P0。用餐者用学号+密码；员工/管理员用授权账号。一期不对接学校 CAS/企业微信/钉钉。角色不能串用。  
  验收：错误密码失败；学生进不了员工/管理端；员工进不了管理端。

- **R09 前面还有几人**  
  P1。展示等待中排在自己前面的人数。不展示「预计 X 分钟」。  
  验收：人数与权威 waiting 且号更小的计数一致。

- **R10 取消与过号**  
  P0。用餐者只能取消「等待中」的号；已被叫到的号不能自助取消。过号后原号立即失效，不自动排回队尾；再吃必须重新取号。  
  **过号触发：**  
  1. 员工随时可手动过号；  
  2. 管理员按窗口配置过号时长（秒）。`0` 或关闭 = 不自动过号。大于 0 时，号被叫到后超过该时长仍未完成，则系统自动过号。默认 `0`。  
  改配置后只影响之后进入叫号的票；已叫号的票沿用进入叫号时记下的超时快照（D15）。  
  验收：等待中可取消且人数减 1；已叫号取消失败；手动/自动过号后原号失效且不回队；配置为 0 时不会自动过号。

- **R11 管理端**  
  P0。维护食堂、楼层、窗口、营业状态、窗口员工授权、用餐者学号账号（含导入），以及窗口过号时长。  
  验收：新建营业窗口后用餐者可见；给员工授权后该员工才能叫该窗口的号；修改过号时长后该窗口按新规则对后续叫号生效。

- **R13 多食堂 / 多楼层**  
  P0。食堂为第一导航维度，楼层为食堂内可选结构。  
  验收：A 食堂窗口叫号不影响 B 食堂人数与当前号。

- **R14 实时通道**  
  P0。队列与窗口状态变化走 WebSocket。容量目标：约 1 万在校生账号规模；午高峰同时在线 **2000–3000** 路 WebSocket。该数字是设计与压测目标，不是已实测 SLA。  
  验收：功能上推送正确、可重连、不因重连重复发号；2000–3000 在线压测作为独立性能门，未跑不得声称已达标。

- **R15 权限隔离**  
  P0。三角色分离；员工绑定窗口。大屏页按窗口订阅，不因打开大屏获得叫号权限。  
  验收：越权调用返回明确失败，队列不被改写。

- **R18 终端形态**  
  P0。用餐者手机浏览器（H5）；员工窗口平板或电脑浏览器；管理员电脑浏览器；大屏为浏览器全屏页。一期不做原生 App、不做小程序。

- **R19 窗口供应说明**  
  P2。窗口可有一句非结构化说明（如「盖饭/面」），不是菜单，不可点选下单。

- **R20 号证与营业日**  
  P1。营业日按学校时区（Asia/Shanghai）自然日 00:00 切分；跨日未完成的号作废，需重新取号。  
  验收：日期切换后旧 waiting/called 不可继续当有效号，新号从 1 开始。

- **R22 窗口大屏页 + 浏览器语音叫号**  
  P0。一期做窗口专用全屏网页：显示窗口名、当前号、等候队列摘要；叫下一号时用浏览器语音播报（例如「请 23 号到 2 号窗口」）。  
  **打开方式（D20）：** 员工为该窗口生成**可吊销展示令牌链接**，电视浏览器打开该链接。大屏不持有员工写权限会话。无令牌、令牌吊销或绑错窗口 → 失败，不降级成全校公开无鉴权。令牌不授予叫号权。  
  明确不包含：指定品牌叫号器、专用喇叭协议、小票打印机、员工账号长期挂在公共屏上。  
  验收：叫号后大屏当前号更新并触发一次播报；刷新/重连不把同一号反复播报（除非员工再次叫该号）；无语音权限或浏览器不支持 TTS 时，大屏数字仍可用并有明确降级提示；吊销令牌后大屏拉数失败。

### 3.2 明确不做（一期，已确认）

- **R16 外卖 / 跑腿**
- **R17 社交评价、推荐、等待时长预测**

## 4. MVP 范围

一期交付真实可上窗的最小闭环：

1. 管理员维护食堂/楼层/窗口/人员/学号账号/过号时长。
2. 用餐者学号登录后，按食堂（楼层）看窗口、人数、当前号（未登录不能看列表）。
3. 取号、查看我的号、取消等待中的号。
4. 员工叫号/完成/过号/暂停。
5. 窗口全屏大屏页 + 浏览器语音播报。
6. WebSocket 推送队列变化。
7. 同一人只能有一个有效号；号段按窗口按日从 1 开始。

不在一期：点餐支付、SSO、小程序/App、实体叫号硬件、小票打印、时长预测、多校区（多食堂已包含）。
