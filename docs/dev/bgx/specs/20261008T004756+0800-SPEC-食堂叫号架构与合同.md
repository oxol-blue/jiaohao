## 2. 拟议结构

```text
用餐者H5 / 员工Web / 管理Web / 大屏Web
        | HTTPS REST + WebSocket
     Nginx（TLS、静态、反代；WS 升级）
        |
     apps/api  模块化单体
        |-- identity
        |-- canteen
        |-- queue     ← tickets 唯一写入口
        |-- realtime  ← 连接与广播，不存队列
        |-- admin
        |
   PostgreSQL（权威）     Redis（Pub/Sub + 可选投影缓存）
```

多实例时：HTTP 无状态；WS 用 Redis 把队列事件送到持有订阅的进程。会话用 JWT 或 Redis session，避免必须粘滞到单机才能叫号。

**保留单体的理由：** 第一期写入口集中在 `queue`，拆微服务会把号段事务和推送拆开，增加双写风险，却解决不了「一人一号」。  
**何时拆 WS 网关：** 单机连接数或事件扇出成为实测瓶颈，且 queue 模块 CPU 仍健康。  
**不采用：** 用 Redis 当票号权威；前端本地发号；每个窗口一个服务。

## 3. 技术栈选项（不锁厂商）

| 方案 | 组成 | 收益 | 代价 | 重评 |
| --- | --- | --- | --- | --- |
| A | TypeScript：Vue/React + Node API；PostgreSQL；Redis；Nginx | 前后端一份 contract；开工快 | 单进程 WS 弱于 Go | 小团队要最短工期且不熟 Go |
| B | Java 21 + Spring Boot 3 + 前端 SPA | 校园接手常见 | 两套语言；一人偏重 | 必须交给只维护 Java 的机房 |
| **C 已选** | Go API + 前端 SPA；PostgreSQL；Redis；Nginx | 连接密度好；静态二进制好部署 | 合同两套语言；要熟 Go；样板少 | 用户 2026-10-08 选定；重评条件：确认无法独立维护 Go 或学校强制其它语言 |

未选云厂商、未选付费推送。Go 侧库（HTTP 框架、pg 驱动、WS、argon2、JWT）实施时再钉版本。

### 3.1 本轮已确认的选型约束（2026-10-08）

- 维护者：自己或很小开发组（Q11）。
- 运行环境：可自装 Docker / Linux 虚拟机（Q12）。
- **主栈：方案 C，Go 后端 + Vue 3 + Vite SPA（Q13/Q14 用户选定）。** 选 Go **不等于** 放弃 Redis 多实例，也不等于单机硬扛 3k 连接。
- HTTP 框架：**chi**（Q14）。WebSocket 库、migrate 工具、JWT 库实施时再钉版本。
- 数据：PostgreSQL 权威；Redis 仅 pub/sub 与投影。无「必须 MySQL」。
- 未锁：具体库版本、云厂商、是否上 Nginx 的发行版。

### 3.2 三个方案对「食堂叫号」分别难在哪

产品真正难的不是 CRUD，而是：

1. **号段事务**：同窗口同日号不重复，一人不能两张有效票（行锁 / 部分唯一约束）。
2. **叫号条件更新**：当前号未完成时不能连叫两号。
3. **按窗口扇出的 WebSocket**：高峰 2000–3000 连接，事件按窗口 topic 推，不是全局广播。
4. **四套界面**：用餐者 H5、员工、管理、大屏 TTS；一个人要改得完。
5. **Windows 上开发、Linux 上跑**（当前工作区在 Windows）。

| 维度 | A TypeScript | B Java Spring Boot | C Go |
| --- | --- | --- | --- |
| 队列事务 | `pg` 事务 + 行锁足够；部分唯一约束在 Postgres，与语言无关 | JPA/JOOQ 都能做；样板多，一人写状态机更慢 | 同样走 SQL；手写多，状态机清晰但要熟 Go |
| 3k WebSocket | 单进程弱于 Go/Java；**2 API 实例 + Redis pub/sub** 就能覆盖设计目标，不需要一上来集群 | 线程/WebSocket 会话稳，内存更吃；校园教程多 | 单机连接密度最好；若你不熟 Go，调试 WS 比写业务还久 |
| 四端 UI + 合同 | 一份 TS 类型给前后端；改错误码只改一处 | 前端仍要 Vue/React，DTO 两套语言对字段 | 同 B，两套语言 |
| 小团队工期 | 最短，和「准备上窗」最贴 | 常见于信息化交接，对一个人偏重 | 中间；生疏时最长 |
| Docker 部署 | Node 镜像小，compose 简单 | JDK 镜像大，习惯后很标准 | 静态二进制最好部署 |
| 风险 | 乱引入 npm 包、单实例硬扛 3k | 过度分层、开工慢 | 人才与样板少 |
| 何时选它 | **默认最贴你现在的约束** | 以后一定交给只维护 Java 的机房 | 你已经能独立写 Go 服务，且坚持单机不水平扩展 |

**不建议为这个产品选：** PHP 请求式假实时、纯前端 setInterval 冒充叫号、Mongo 当号段权威、Firebase 一类付费推送（未授权云厂商）、第一期上 Kafka。

**数据库与 Redis（与 A/B/C 正交）：** 号段和「一人一有效票」更吃 PostgreSQL 的部分唯一索引；Redis 只做 pub/sub 和缓存。没有「必须 MySQL」时不要为熟悉而换库。MySQL 能做，但约束写法更别扭，不是这个产品的收益点。

前端已选 **Vue 3 + Vite**。Nginx 在 Docker 里当 TLS 与静态入口。

**Go 合同策略：** 不再使用「一份 TypeScript 类型前后端共用」。权威合同为 OpenAPI（HTTP）+ 本文事件名（WS）。前端生成或手写 TS 类型对照；Go 用结构体 + 测试断言字段名。禁止两套各写各的错误码。

### 3.3 选定后的拟议骨架

```text
apps/web/          # Vue 3 + Vite：用餐者/员工/管理/大屏路由
apps/api/          # Go + chi：HTTP + WebSocket 模块化单体
api/openapi.yaml   # HTTP 合同权威
docs/dev/bgx/
```

HTTP：**chi**（贴 `net/http`）。**不采用 Fiber**。WS 库（gorilla/websocket 或等价）、迁移（golang-migrate 或 goose）、密码 argon2id：实施时钉版本，不在规划里锁 minor。

## 4. 数据所有者与主要表（拟定）

权威在 PostgreSQL。Redis 可缓存 `window:{id}:summary`（current_number, waiting_count, status），**写失败或缓存缺失时回源 DB**。

- `users`：id, student_id UNIQUE, password_hash, role(`diner|staff|admin`), status
- `canteens`：id, name, sort
- `floors`：id, canteen_id, name, sort；食堂可无楼层
- `windows`：id, canteen_id, floor_id NULL, name, code, status(`open|pause_take|closed`), skip_timeout_seconds DEFAULT 0, blurb, sort
- `staff_window_grants`：user_id, window_id
- `window_day_counters`：window_id, business_date, next_number；分配号时行锁
- `tickets`：id, window_id, user_id, business_date, number, status, created_at, called_at, finished_at, cancel_reason, announcement_id

部分唯一：同一 `window_id + business_date + number`。  
部分唯一：同一用户至多一张 `status IN ('waiting','called')` 的票（数据库约束或等价事务检查）。

营业日按学校时区自然日 00:00 切分（REQ R20 已确认）。

## 5. 状态机

### 5.1 票 `tickets.status`

```text
waiting --cancel(diner,仅waiting)--> cancelled
waiting --call_next(staff)-------> called
called  --complete(staff)--------> completed
called  --skip(staff|auto)-------> skipped
waiting|called --day_close------> expired
```

禁止：completed/skipped/cancelled/expired 再变回 waiting；skipped 不回队尾；diner 取消 called。

有效号 = `waiting` 或 `called`。排队人数 = 该窗口当日 `waiting` 数（不含 called，因已在窗口侧）。若产品要把「已叫未到」算进人数，与 REQ R02「等待中」冲突，保持不含 called。

### 5.2 窗口 `windows.status`

- `open`：可取号、可叫号
- `pause_take`：不可新取号，可叫已有 waiting
- `closed`：不可新取号；**当日已发出 waiting 可继续叫完**（D21）。一期不强制批量过号。`pause_take` 同此：不可新取，可叫已有 waiting。

### 5.3 过号时长

`skip_timeout_seconds`：0 = 不调度自动过号。>0 时，`called_at + timeout` 到期且仍为 called → skip。  
**改配置后：** 只作用于**之后**进入 called 的票（落实 REQ 原文）。已叫号的票继续用进入 called 时记下的超时快照（列 `skip_after` 或等价）。这关闭 Q10。

## 6. 关键链路（拟议）

### B01 取号（R03/R08）

登录 diner → 选食堂/楼层/窗口（列表接口同样要会话，D22）→ `POST /tickets`  
失败：未登录（浏览或取号均为 `UNAUTHENTICATED`）、窗口非 open、已有其它窗口有效号 → `HAS_ACTIVE_TICKET`、暂停取号。`closed`/`pause_take` 仍可叫当日 waiting，不可新取。  
成功：若本窗口已有有效号则原样返回（幂等）；否则锁当日计数器，number+1，插 waiting，广播 `queue.window.updated` 与 `queue.ticket.updated`。  
结果：我的号页看到号码。

### B02 叫下一号 + 大屏语音（R06/R22）

staff 授权窗口 → `POST /windows/{id}/call-next`（条件：当前 called 必须先 complete/skip）  
成功：最早 waiting 变 called，写 `called_at`、`skip_after`、新 `announcement_id`，广播含 announcement。  
大屏：更新数字；若本地 last_announcement_id 不同则 TTS 一次。  
失败：无 waiting、无授权、已有 called 未处理。

### B03 取消（R10）

diner `POST /tickets/{id}/cancel` 仅 waiting。人数-1。called 返回 `TICKET_NOT_WAITING`。

### B04 过号（R10）

手动：staff skip 当前 called。自动：调度器选 `skip_after <= now() AND status=called`。都不回队。广播更新。

### B05 管理员建窗并授权（R11）

admin 建 canteen/floor/window → 授权 staff → diner 列表可见（open 时）→ 该 staff 才能 call-next。

失败路径共通：超时/重复提交用幂等键或条件更新；重启后未 ACK 的 WS 事件以 REST 快照为准。

## 7. HTTP 合同（v1 草案）

公共包络：

```json
{ "ok": true, "data": {}, "error": null }
{ "ok": false, "data": null, "error": { "code": "HAS_ACTIVE_TICKET", "message": "你已有未完成的号码" } }
```

鉴权：`Authorization: Bearer <token>`。角色不够 → `FORBIDDEN`；无会话 → `UNAUTHENTICATED`。

### 7.1 身份

`POST /api/v1/auth/login`  
请求：`{"student_id":"20260001","password":"..."}`  
成功：`{"token":"...","user":{"id":"...","role":"diner","student_id":"20260001"}}`

`POST /api/v1/auth/logout`

### 7.2 浏览

均需 diner/staff/admin 会话（D22）。未登录 → `UNAUTHENTICATED`。

`GET /api/v1/canteens`  
`GET /api/v1/canteens/{id}/floors`  
`GET /api/v1/windows?canteen_id=&floor_id=`  
窗口摘要字段：`id,name,code,status,blurb,current_number,waiting_count,canteen_id,floor_id`

### 7.3 取号与我的号

`POST /api/v1/tickets` `{"window_id":"..."}`  
成功：票对象（含已有票）。

`GET /api/v1/me/ticket` 无有效票时 `data: null`。

`POST /api/v1/tickets/{id}/cancel`

票对象：

```json
{
  "id": "t_1",
  "window_id": "w_2",
  "canteen_id": "c_1",
  "window_name": "二号窗口",
  "number": 23,
  "status": "waiting",
  "current_number": 18,
  "people_ahead": 4,
  "business_date": "2026-10-08"
}
```

`people_ahead`：同窗口同日 `waiting` 且 `number` 更小的数量（R09）。

### 7.4 员工

`GET /api/v1/staff/windows` 仅授权窗口。  
`POST /api/v1/windows/{id}/call-next`（`open`/`pause_take`/`closed` 只要当日仍有 waiting 即可，D21）  
`POST /api/v1/windows/{id}/complete` 完成当前 called  
`POST /api/v1/windows/{id}/skip`  
`POST /api/v1/windows/{id}/pause-take`  
`POST /api/v1/windows/{id}/resume-take`  
`POST /api/v1/windows/{id}/display-token` 生成或轮换展示令牌（员工，本窗授权）  
`DELETE /api/v1/windows/{id}/display-token` 吊销

双击 call-next：第二次应得到 `CALLED_PENDING`（仍有 called 未完成），不得连续叫两号。

### 7.5 管理

食堂/楼层/窗口 CRUD；`PUT /api/v1/windows/{id}/skip-timeout` `{"seconds":0}`；  
`POST /api/v1/users/import` 学号账号；`PUT /api/v1/staff/{userId}/windows` 授权列表。

### 7.6 大屏只读

`GET /api/v1/display/windows/{id}` 必须带该窗口展示令牌（query 或 header）。无令牌、吊销、绑错窗口 → `DISPLAY_TOKEN_INVALID`，**不**公开无鉴权（D20）。  
WebSocket 订阅 `display:{windowId}` 同样校验收令牌，不接受员工写会话当大屏凭证。

错误码闭集（可增不可改义）：`UNAUTHENTICATED FORBIDDEN VALIDATION_ERROR WINDOW_NOT_OPEN WINDOW_PAUSE_TAKE HAS_ACTIVE_TICKET TICKET_NOT_WAITING TICKET_NOT_CALLED NO_WAITING CALLED_PENDING NOT_FOUND CONFLICT DISPLAY_TOKEN_INVALID`。

## 8. WebSocket 合同（草案）

连接：`GET /api/v1/ws?token=` 或首帧 `{"type":"auth","token":"..."}`。  
订阅：`{"type":"subscribe","topics":["window:w_2","ticket:mine","display:w_2"]}`  
服务端可拒绝未授权 topic。

事件：

```json
{
  "event": "queue.window.updated",
  "window_id": "w_2",
  "current_number": 23,
  "waiting_count": 12,
  "status": "open"
}
```

```json
{
  "event": "queue.ticket.updated",
  "ticket": { "id": "t_1", "status": "called", "number": 23 }
}
```

```json
{
  "event": "queue.announcement",
  "announcement_id": "a_9",
  "window_id": "w_2",
  "window_name": "二号窗口",
  "number": 23,
  "text": "请 23 号到 二号窗口"
}
```

重连：先 REST 拉窗口摘要与我的票，再 subscribe；TTS 仅当新 `announcement_id`。

## 9. 容量与实时（拟议）

目标 2000–3000 连接，不是 1 万同时连接。假设：

- 多数连接订阅 1 个窗口 + 自己的票；
- 叫号频率按窗口，全校同时叫号事件远小于连接数；
- 广播按 window topic 扇出，不全局 flood。

单 Go API 实例通常可尝试该连接量，**待实测**。计划：2 个 API 实例 + Redis pub/sub 作为水平扩展默认，而不是一开始上独立 WS 集群。选 Go 不等于单机硬扛。

压测未跑前禁止把 S06 标完成。

## 10. 安全边界

- diner 只能取消自己的 waiting 票。
- staff 的 window_id 必须在 grants 内，每个写接口检查。
- admin 不能冒充 diner 取号（除非明确运维接口，一期不做）。
- display token 只读。
- 导入文件与 blurb 长度限制，防过大 payload。

## 11. 未决 / 待实测

- 技术栈已选 C（Go + Vue 3 + chi + PG + Redis）；库 minor 版本未锁。
- 大屏打开方式：已选定展示令牌链接（D20）。
- closed 窗口已取号：已选定可继续叫完当日 waiting（D21）。
- 窗口列表：已选定必须登录（D22）。
- 2000–3000 连接的真实内存与 Redis 扇出。
- 浏览器 TTS 中文语音质量随设备变化，只保证「尝试播一次 + 数字可读」。
- 展示令牌存储与轮换周期：实施时钉（哈希入库、可轮换）；不在规划锁 TTL 产品值。
